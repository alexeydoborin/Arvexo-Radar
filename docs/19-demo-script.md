# Arvexo Radar: сценарий демонстрации

**Версия:** v0.3.0 — Enterprise Effectiveness MVP
**Аудитория:** жюри КРОК, CTO, AI Platform Owner, FinOps
**Длительность:** основной путь 8–10 минут, вопросы — отдельно
**Адрес:** `radar.arvexo.ru` → «Войти» (Arvexo Account) → `/app`

## 1. Цель демонстрации

Показать путь от использования AI до денег: **использование → надёжность → результат → окупаемость**, а затем — как успешный опыт одних сотрудников превращается в практику для всей компании. Всё это без скрытых допущений: каждая цифра имеет формулу, источник и статус (`actual` / `estimate` / `mixed` / `demo`).

Главная мысль, которую нужно донести: **Radar не ещё один дашборд токенов и latency. Он отвечает IT-директору, окупается ли AI и что именно масштабировать.**

## 2. Подготовка (за день и за час до показа)

За день:

- войти под своей учётной записью на прод и пройти весь сценарий один раз;
- убедиться, что `GET /api/v1/health` возвращает `{"status":"ok"}`;
- проверить, что последний запуск CD на `main` зелёный;
- подготовить локальный запасной стенд (проверен 18.09.2026, см. раздел 8): `docker compose up -d db api worker`, затем `docker compose exec api python -m app.seed_demo`, фронтенд запускается отдельно (`npm run dev` в `frontend/`);
- подготовить небольшой CSV с запросами для необязательного шага 9 и заранее загрузить его один раз;
- **записать скринкаст или сделать скриншоты** экранов шагов 2–7: это главный запасной вариант, потому что локальный стенд тоже требует входа (раздел 8);
- за день ничего не менять в `frontend/` и не деплоить: слабые места раздела 7 известны и учтены в сценарии.

За час:

- открыть `/app` в чистом окне, убедиться, что вход проходит и Home загружается;
- period в фильтрах — июль 2026 (`2026-07-01 … 2026-08-01`), это период demo-набора;
- закрыть лишние вкладки и уведомления, включить масштаб браузера 110–125 %.

## 4. Сценарий

### Шаг 1. Открыть Radar (30 с)

**Показать:** лендинг → вход через Arvexo Account → экран выбора режима: «Посмотреть демо» и «Загрузить свой датасет». Оба режима доступны только после входа.
**Действие:** выбрать «Посмотреть демо».
**Сказать:** «Radar — аналитический слой над AI-шлюзом компании. Он не читает содержимое промптов и не оценивает сотрудников. Он отвечает на вопрос: окупается ли AI и что масштабировать».
**Заранее оговорить:** «Показываю синтетический, но внутренне согласованный набор за июль 2026, он везде помечен как demo».

### Шаг 2. Home: вывод для руководителя (1 мин)

**Показать:** экран **Home**, показатели Model Health / Total Requests / Incidents / Avg. Latency, график запросов, Recent Incidents, Recommendations.
**Сказать:** «Первый экран — короткий ответ: что происходит с AI сегодня и что требует внимания».
**Осторожно:** процентные изменения рядом с карточками на Home (↑ +12 %, ↓ −18 % и т. п.) в текущей версии — статичные значения макета, не расчёт. **Не называть их вслух как динамику.** См. раздел 7.

### Шаг 3. Аналитика: главная цепочка (2 мин)

**Действие:** **Analytics** (раздел «Эффективность ИИ»).
**Показать:** блоки «Использование и расходы» и «Бизнес-эффект»: MAU, запросы, агенты, затраты A → Time Saved, FTE Saved, B, Net Benefit, ROI.
**Сказать:** «Цепочка читается слева направо: используют ли → сколько стоит → сколько времени сэкономлено → сколько это в деньгах → окупается ли. Вывод: B > A, чистый эффект ≈ 1,1 млн ₽ за месяц».
**Ключевое:** навести на значок формулы у показателя. FTE Saved — *эквивалент высвобождённого времени, а не сокращение штата*. Затраты A — не только токены, но и инфраструктура, подписки, поддержка (команда разработки исключена настройкой методики).

### Шаг 4. Models: где деньги, а где убыток (1,5 мин)

**Действие:** **Models** (раздел «AI-агенты»).
**Показать:** четыре агента, стоимость, экономия, ROI, error rate, latency.
**Сказать:** «Средний ROI скрывает разброс. Отрицательны сразу два агента: CRM-ассистент и Навигатор знаний (у второго пока мало данных, поэтому статус «недостаточно данных», а не «убыточный»). Агент договоров и Report Copilot дают почти весь эффект. CRM-ассистент при 14,6 % ошибок и 320 тыс. ₽ затрат приносит 130 тыс. ₽ — это убыток 190 тыс. ₽. Radar показывает, что оптимизировать или останавливать».
**Вопрос, который нужно предупредить:** «Почему CRM-ассистент так много используется, но не окупается?» → много запросов ≠ результат (повторы из-за ошибок).

### Шаг 5. Monitoring: подразделения и внедрение (1 мин)

**Действие:** **Monitoring** (раздел «Подразделения»).
**Показать:** разрез по подразделениям.
**Сказать:** «Юридический отдел даёт 32 % денежной экономии при 20 % затрат. HR показывает высокий интерес, но подтверждено только 34 % экономии. Radar разделяет “хотят пользоваться” и “доказанный эффект”».

### Шаг 6. Incidents и Recommendations (1,5 мин)

**Действие:** **Incidents** (раздел «Инсайты»), затем **Recommendations**.
**Показать:** инсайты с формулировкой наблюдения; каталог AI Best Practices со статусами `detected → under_review → approved → published`.
**Сказать:** «Radar находит повторяемые успешные сценарии: “Проверка договоров по единому чек-листу” (Impact Score 96), “Сбор управленческого отчёта из нескольких источников” (93). Практика создаётся, только если одновременно выполнены пороги: Impact ≥ 70, ≥ 8 использований, ≥ 3 пользователей, успешность ≥ 80 %, ошибок ≤ 20 %, оценка ≥ 4,0. Текст промптов не раскрывается».
**Действие (по желанию):** у практики «Проверка договоров…» (статус «Согласована») нажать «Рекомендовать другим подразделениям», выбрать подразделения; после этого практика публикуется. Делать только на локальном стенде или заранее решить, что демо-данные на проде можно менять.
**Сказать:** «Это и есть Knowledge Sharing: опыт одних сотрудников становится рекомендацией для всей компании, с владельцем и отслеживанием внедрения».

### Шаг 7. Settings: как считается результат (1 мин)

**Действие:** **Settings** (раздел «Настройки методики»).
**Показать:** экономическая модель, «Как считается результат», тарифы моделей, нормативы сценариев, стоимость FTE (400 000 ₽ в месяц по умолчанию).
**Сказать:** «Формулы и допущения не зашиты в код. Финансовый директор может изменить стоимость FTE или включить команду разработки в TCO, и весь ROI пересчитается. Экономия строится от завершённых задач и норматива “до/после AI”, а не от числа токенов».

### Шаг 8. Integrations: что реально подключается (30 с)

**Действие:** **Integrations** (раздел «Источники данных»).
**Сказать:** «Факт сегодня — telemetry AI-шлюза (OpenAI-совместимый proxy). HR-справочник, FinOps, реестр подписок и бизнес-системы — это интеграции для production, и мы прямо помечаем, что в demo они смоделированы».

### Шаг 9. Необязательно: собственный датасет (1–2 мин)

Показывать только если предыдущие шаги прошли гладко и есть время.

**Действие:** «Загрузить датасет» → подготовленный CSV → validation/preview → запуск анализа → результат на Home.
**Сказать:** «Это отдельный режим: Radar классифицирует запросы, группирует их в сценарии и находит проблемные места. Секреты и персональные данные маскируются до анализа».
**Проверено на локальном стенде:** CSV из 72 строк → validation → run на mock-провайдере → результат за секунды; email и ключ в тексте заменяются на `[EMAIL_1]` и `[SECRET_1]` и не попадают в overview и prompt-health; PDF генерируется. Загрузку через кнопку в интерфейсе (выбор файла) прогоните вручную заранее: я проверял тот же путь через API.
**Оговорка (обязательна):** «Классификация и кластеризация в MVP — объяснимый baseline (keyword-fallback, hashing-эмбеддинги). Семантическая модель выбирается после аудита реального датасета». Если спросят про очень длинные запросы — chunking записей в 100k токенов **ещё не реализован** (см. FAQ).

### Шаг 10. Итог (30 с)

**Сказать:** «Три вещи: Visibility — как используют AI; Business Value — окупается ли; Knowledge Sharing — что масштабировать. Всё с формулой, источником и честной пометкой, что доказано, а что оценка».

## 6. Запрещённые утверждения

- «Мы первые / единственные, кто связывает технические, бизнес- и продуктовые метрики AI», «первые с AI-generated RCA». Похожие возможности частично есть у Fiddler, Datadog, Dynatrace, Arize, а в России у Proto и Artimate (см. [research](../ARVEXO_RADAR_RESEARCH_2026.md)).
- «Экономия ≈ 2,27 млн ₽ — это реальный результат компании». Это синтетический demo-набор; benchmark не доказывает причинность.
- «AI заменит N сотрудников». FTE Saved — эквивалент времени, не сокращение штата.
- «Технический success rate — это качество бизнес-результата».
- «Система гарантирует обнаружение всех секретов/PII».
- «Модель классифицирует с точностью N %». Оценка на размеченном датасете не проводилась.
- «Это production-ready enterprise deployment». Production требует SSO/RBAC, интеграций и retention-политики.
- «Данные КРОК показывают…». Используется синтетический набор, тексты запросов КРОК не использовались.
- «Динамика +12 % к прошлому периоду». См. раздел 7.
- «Radar оценивает эффективность сотрудников». Нет: только организационная аналитика.

## 8. Отказоустойчивость

- **Основной путь:** прод `radar.arvexo.ru`.
- **Запасной путь 1 (скринкаст/скриншоты):** самый надёжный. Говорить прямо: «показываю сохранённую запись».
- **Запасной путь 2 (локальный стенд):** `docker compose up -d db api worker` + `docker compose exec api python -m app.seed_demo` + `npm run dev` в `frontend/` (порт 3000, иначе CORS backend блокирует запросы). Данные идентичны прод-набору, цифры проверены. **Но `/app` и здесь требует сессию Arvexo Account:** `ARVEXO_AUTH_MODE=demo` относится только к backend, фронтенд его не читает. Локальный SSO (`localhost:8032`) отвечает `CLIENT_NOT_FOUND`, пока в нём не зарегистрирован клиент `arvexo-radar`. Зарегистрируйте клиент и убедитесь, что вход работает, заранее.
- Полный `docker compose up --build` (с сервисом `web`) на вашей машине зависает на `npm install` в Dockerfile фронтенда (нет `package-lock.json` в слое установки, медленный npm-реестр). Не рассчитывайте на него в день показа.
- Внешний LLM для основного сценария не нужен: demo-аналитика и формулы работают локально.
- Отказ SSO: работать с локальным стендом; не пытаться обходить вход на проде.
- В любом fallback явно называть режим (prod / локальный demo / снимок).
